## 1. 项目业务与边界

### 1.1 一句话说明

把分散的营地资料整理成可检索、可核对的知识，再结合地图查询和业务工具，帮助用户完成咨询，并把需要人工处理的问题交给客服。

项目服务三个角色：

| 角色 | 业务需求 | 系统提供的能力 |
| --- | --- | --- |
| 游客 | 找营地、了解交通设施、询问宠物与退订规则、提交投诉 | 地点查询、资料问答、工单草稿与确认、进度查询 |
| 客服 | 减少重复查资料，处理需要人工判断的问题 | 查询公开及内部资料，查看和处理工单 |
| 运营 | 维护营地信息，避免旧规则继续被使用 | 上传资料、检查提取结果、审核发布、版本更新和下架 |

### 1.2 两种数据不能混用

| 数据 | 示例 | 来源与边界 |
| --- | --- | --- |
| 地点事实 | 名称、城市、地址、坐标 | 高德MCP；查询时间不等于事实更新时间 |
| 经营规则 | 宠物、退订、入住时间、收费说明 | 对应营地审核发布的资料；不能从地图名称推断 |

**地图上有这个营地，不代表系统掌握它的经营规则。**

业务示例：

- “杭州哪里有露营地？”——查询地图地点。
- “某营地能带狗吗？”——先确认营地身份，再查该营地规则。
- “帮我投诉这个营地。”——整理工单草稿，用户确认后提交。
- “周六还有营位吗？”——目标方案需要实时库存接口；没有接口时明确说明无法确认。

## 3. 架构与业务问答

### Q1. 为什么做RAG，普通数据库查询不够吗？

**参考回答：**

数据库适合管理结构化字段，例如营地名称、城市、设施和工单状态。但退订条件、宠物限制、恶劣天气处理等规则，通常存在于文档中，用户的问法也不固定。

因此把结构化事实交给查询工具，把文档规则交给RAG。先找依据，再生成回答，避免让模型凭记忆解释营地政策。

**继续追问：为什么不把所有资料放进Prompt？**

资料增长后，全部放入会增加上下文长度、费用和干扰，而且难以区分不同营地、版本和权限。检索的目的是只提供本轮真正需要且允许使用的资料。

**要理解：**数据库、检索和模型分别承担不同职责，不是由模型替代所有查询。

### Q2. RAG是否必须使用向量数据库？

**参考回答：**

不必须。RAG的核心是先检索外部知识，再基于知识生成回答。检索可以采用BM25，也可以采用向量或混合检索。

当前版本采用BM25，属于关键词检索增强生成。Qdrant已做基础组件验证，但真实向量化和专用重排序尚未完成完整联调。

| 组件 | 职责 |
| --- | --- |
| Embedding模型 | 把文本转换成用于语义比较的向量 |
| 向量数据库 | 存储向量及元数据，执行相似性检索 |
| 大语言模型 | 理解问题、选择工具、结合证据组织回答 |

**调用DeepSeek对话接口，不等于已经完成Embedding。**

### Q3. 为什么需要Agent，而不只是一个问答接口？

**参考回答：**

用户可能连续完成不同任务：先找营地，再查看第二个地点，继续询问规则，最后提交咨询。系统需要根据意图调用不同工具，并维护当前选择。

我没有让模型自由操作数据库，而是提供受控工具，例如搜索营地、检索资料、准备草稿、查询本人工单。明确的地图查询可以直接返回结构化卡片，只有需要语言理解和组织的任务才经过模型。

**要理解：**Agent的价值在于协调工具完成任务，不在于让所有请求都多调用几次模型。

### Q4. 一条完整请求是怎么走的？

以“这个营地能带狗吗”为例：

**参考回答：**

首先确认当前用户选中的是哪个营地；其次按照营地ID、用户权限和当前发布版本筛选知识；然后检索相关片段，将证据交给模型生成回答；最后检查引用是否属于本次允许使用的资料，再返回答案和原文入口。

如果没有该营地的可靠规则，就明确说明资料不足，不套用其他营地的宠物政策。

```text
资料链路：
上传 → 解析/OCR → 清洗与分块 → 人工审核 → 发布 → 可检索

咨询链路：
用户提问 → 确认营地和意图 → 查询工具/检索资料 → 回答与引用
                                      ↓
                              需要人工处理 → 工单草稿 → 用户确认
```

## 4. 数据治理与RAG问答

### Q5. “10+类数据”具体是什么？

需要区分**业务类别**和**文件格式**。

项目资料清单包含12类公开业务内容：营地概况、交通停车、收费说明、宠物规定、预订流程、改期取消、入住离场、设施使用、消防规定、亲子须知、天气与闭园通知、投诉服务；另有内部资料。

**参考回答：**

“多类”主要指业务内容分类，不是十几种文件格式。不同类别需要保留营地归属、公开或内部权限、来源、版本等信息。

文件解析分别处理文本、Word、PDF和图片。图片、扫描页先提取文字，再进入统一的文本检索链路。

**当前限制：**61份种子资料是虚构演示资料，不能介绍成采集了61份真实经营文件，也不代表服务器已全部审核发布。

### Q6. 多模态数据怎么处理？

**参考回答：**

当前主要采用“多种输入统一转文本”的方式。Word提取段落和表格，文字型PDF提取正文，扫描PDF和图片使用OCR，再对提取结果进行审核。

这与直接理解图片内容、检索图片向量的原生多模态RAG不同。当前重点是把规则牌、截图等内容转成可检索文本。

**目标方案需要解决：**

- OCR错字，尤其是金额、日期、否定词和电话号码。
- 表格行列关系，避免价格和套餐对应错误。
- 原文位置，方便核对。
- 文件尺寸、页数和解析失败，避免异常文件拖垮服务。

**面试边界：**识别成功一张图片，不等于复杂多模态数据治理已全面验收。

### Q7. 知识怎么分块，为什么这样分？

**当前实现回答：**

目前优先按空行划分段落并合并短段，超过约800字符的长段再切分，长段切分保留80字符重叠。这样实现简单，能尽量保留局部上下文。

这个参数还不是通过充分实验得出的最优值。下一步会针对营地规则，比较不同分块方式对召回和回答正确性的影响。

**继续追问：分块太大、太小有什么问题？**

太小容易把条件和结论拆开，例如只检索到“可以退款”，却丢掉“提前48小时”的条件；太大会引入无关内容，增加模型阅读成本和混淆概率。

**目标优化原则：**一条完整规则及其适用条件尽量放在同一片段，表格保留必要表头。

**注意：**上述800和80是字符口径，不是token数量；也不是所有段落之间都固定重叠80字符。

### Q8. BM25是什么，为什么会漏召回？

**参考回答：**

BM25根据关键词在片段中的出现情况、关键词稀有程度和片段长度计算相关性。它对营地名称、明确业务词和编号比较有效。

问题是用户可能说“提前三天退掉”，文档却写“取消预订”；用户说“狗狗”，文档写“宠物”。词面不一致时，就可能漏召回。

**项目已有例子：**

早期评测中，口语与复杂题在限定营地后的Hit@5为22/26，漏召回涉及退订、宠物和离场等口语表达。这说明模板问题得分高，不代表自然问法也能处理好。

**继续追问时要会解释：**

- 词频反映某个词在当前片段里出现多少次。
- 逆文档频率降低普遍词的区分权重，突出较少出现的词。
- 长度归一化避免长片段仅因字数多就占优。
- 当前中文处理采用单字与相邻双字组合，不能介绍成已部署专业语义分词模型。

### Q9. 混合检索和重排序准备怎么实现？

**目标方案回答：**

两路召回：BM25负责明确关键词，向量检索补充语义相近但用词不同的表达。两路都先应用营地、权限和版本约束，再合并候选。

合并可以采用RRF，按候选在各路列表中的名次融合，避免直接相加量纲不同的分数。随后用重排序模型同时读取问题和候选片段，进一步判断相关性，再选出少量证据给大模型。

重排序只处理前面召回的候选，不能找回根本没有被召回的正确资料。

```text
问题 → 营地/权限/版本约束
                 ├─ BM25召回
                 └─ 向量召回
                       ↓
                 去重与RRF融合
                       ↓
                    重排序
                       ↓
               少量证据 → 模型回答
```

可以从每路召回20条、融合后最多40条、最终选5条作为实验起点，具体数量根据固定开发集调优，不把这些数字说成通用最优配置。

**继续追问：怎么证明混合检索更好？**

用同一套独立标注问题，分别比较BM25、纯向量、混合检索、混合加重排序，观察Hit@5、排序质量、最终回答正确性、延迟和成本。没有提升，就不因为技术更复杂而保留它。

参考：[Qdrant混合查询](https://qdrant.tech/documentation/search/hybrid-queries/) · [混合检索与重排序](https://qdrant.tech/documentation/tutorials-basics/reranking-hybrid-search/)

### Q10. 怎么解决大模型幻觉？

建议使用“降低无依据回答风险”，避免承诺彻底解决。

**参考回答：**

我主要从证据、权限和输出约束三个环节降低风险。首先核实营地身份，避免检索错对象；其次只提供当前用户可见、当前已发布的资料；最后要求规则回答携带合法引用，没有依据时说明缺口。

但引用合法只说明来源存在，不自动说明模型对原文的解释正确，所以仍需要逐题核对答案是否受到证据支持。

例如原文是“仅指定区域允许明火”，回答成“允许明火”，即使引用正确，也可能误导用户。

**要理解：有引用，不等于有充分依据。**

### Q11. 知识更新后，怎么避免继续回答旧规则？

**参考回答：**

当前通过文档版本和当前发布版本指针控制检索范围。新资料先解析、审核，发布后才成为当前可用版本；历史引用可以保留查看，但不能当作当前政策。

目标接入向量索引后，要先完成新版本索引并确认可用，再切换当前发布版本。索引失败时保留旧版本，不让用户检索到半成品。

**继续追问：数据库和向量库怎么保证一致？**

两个系统不能简单依靠一个本地事务实现原子提交。需要明确索引状态、幂等任务和失败重试，并用当前发布版本做可见性控制。旧向量即使暂未清理，也不能因为版本过滤失效而参与当前回答。

### Q12. 资料互相冲突怎么办？

**目标方案回答：**

不交给模型随意选择。先按照营地身份、适用时间、资料状态和业务责任方确定优先级。

如果两份有效资料仍然冲突，就标记冲突并交给运营确认；回答时说明无法确认，而不是把两份内容拼成一个看似完整的结论。

“平日规则”和“节假日特别规则”可能只是适用范围不同，不能一概当成冲突。

## 5. Agent与业务安全问答

### Q13. 多轮对话里的“第二个”和“它”怎么处理？

**参考回答：**

“第二个”必须对应当前用户、当前会话刚展示的结果顺序，不能让模型凭印象重新找一个营地。

当前地图上下文保留10分钟，记录候选顺序和已选地点；上下文过期、用户换了查询或身份不匹配时，需要重新选择。模型历史用于语言理解，后端状态用于确认真实业务对象。

这样可以避免把上一轮、其他用户或另一个城市的“第二个”混进来。

**当前限制：**地点选择上下文保存在进程内；多副本部署或进程重启的连续性需要另外处理。

### Q14. 为什么模型不能直接提交投诉工单？

**参考回答：**

模型可能误解用户意图，也可能把一句抱怨当成提交请求。因此模型只准备草稿，用户看到营地、类型和内容后，点击确认才创建正式工单。

确认接口检查当前用户是否拥有草稿。重复点击返回同一张工单，事务和行锁用于防止并发确认产生重复记录。

**要理解：**模型负责理解和整理，后端负责权限、状态和正式写入。

**继续追问：回答失败时会不会替换原来的草稿？**

草稿先暂存准备，回答通过后再保存；草稿替换与会话消息写入短事务，写入失败回滚。不能让一次失败的模型回答破坏用户原来可确认的草稿。

### Q15. 模型一直调用工具怎么办？

**参考回答：**

当前实现对工具循环轮数和单轮调用数量设上限，工具参数在后端校验。达到限制后停止继续调用，并提示用户缩小问题。

目标方案还要设置整次请求的时间和成本预算。外部服务超时需要明确失败，不能用演示结果伪装成真实查询结果。

**要理解：**限制循环同时控制死循环、延迟和费用；工具白名单和参数校验不能只靠提示词。

### Q16. “实时同步业务数据”到底怎么实现？

需要分三类：

| 数据 | 合适的获取方式 |
| --- | --- |
| 地址、坐标等地点信息 | 按需调用地图接口，显示查询时间 |
| 宠物、退订等规则 | 有版本的审核发布流程 |
| 实时余位、订单、当日报价 | 直接调用经营系统接口 |

**目标方案回答：**

实时余位不能靠把数据库定期转成文档再让模型猜。用户提供日期、人数、营位类型后，后端直接查询库存与报价接口，明确结果的适用时间和条件。

当前没有接入真实库存和支付系统，因此只能做预订咨询，不能承诺库存锁定或实际预订完成。

未来做正式预订，还需要库存锁定、重复下单、支付超时和订单状态核对，已超出单纯RAG问答。

### Q17. 项目遇到的一个具体难点是什么？

准备自己能讲透的案例，按“现象—复现—原因—修改—验证”展开。

#### 案例A：没有正确资料，却返回502

早期系统把“检索到了候选”误当成“存在可用证据”，遇到未收录营地时仍要求模型引用资料，最后触发引用错误。

改进思路是区分检索候选、足够证据和资料缺口。没有目标营地的可靠依据时，正常返回缺少资料的说明，而不是报系统故障或套用其他营地规则。

#### 案例B：BM25重复统计导致查询变慢

原实现存在重复计算词频统计的问题。优化为每轮查询集中统计相关词项，保留原评分公式和稳定排序。

同一合成语料的500片段单次测试从约7.8秒降到163毫秒，但这是检索微基准，包含JVM预热差异，不能直接写成线上完整问答速度提升。

证据：[缺陷修复与验收记录](BUGFIX-ACCEPTANCE-2026-11-09.md)。

## 6. 四项预期成果的实现与统计

本节全部为目标方案。不能将计算公式、实现机制或示例参数介绍成已取得的运营成绩。

### Q18. “平均8分钟缩短至3秒”怎么实现？

#### 先定义口径

将指标定义为“用户发出咨询，到收到可用完整答复”的耗时，分别记录排队、检索、工具调用和模型生成时间。

首字出现时间和完整回答时间分开统计，不能用流式首字速度代替任务完成速度。人工与智能体都使用相同的起止定义；不同问题类型分别报告。

#### 实现方法

1. **缩短找资料的时间**：资料集中管理，检索直接定位相关规则。
2. **减少不必要的模型调用**：明确的地址、营地列表直接走查询接口。
3. **控制证据数量**：只给模型必要片段，减少输入、输出和无关干扰。
4. **控制工具循环**：避免简单问题反复检索和推理。
5. **合理缓存**：只缓存允许缓存、变化较慢的内容；规则更新后失效，库存不使用过期答案。
6. **分别优化慢环节**：依据分段耗时决定先优化检索、模型还是外部接口。

#### 为什么可能提升

人工流程中存在排队、翻资料和整理文字的时间；自动查询可以压缩这些环节。但模型生成和外部接口仍有延迟，所以3秒需要按问题类型、负载和分位数验证，不能承诺所有问题都在3秒内。

#### 怎么验证

- 用固定问题集记录完整响应时间，并单列失败、超时和重试。
- 同时报告平均值、P50、P95、3秒内比例和样本数。
- 对直查、知识问答、多工具任务分别统计。
- 在串行基线后补充目标并发条件下的测试。

**当前可讲的数据：**早期完整对话评测P95为4.40秒；另一轮地图直查P95为280毫秒。链路和样本不同，不能混用。

### Q19. “人工重复咨询工作量减少60%”怎么实现？

#### 先定义工作量

优先使用“每100次咨询所需的人工处理工时”，同时统计重复咨询的转人工比例。避免上线后咨询总量下降，却被误认为是系统降低了人工工作量。

```text
人工工时降低率
=（上线前每100次咨询人工工时－上线后每100次咨询人工工时）
 ÷ 上线前每100次咨询人工工时
```

#### 实现方法

- 自动回答交通、入住、宠物等资料明确的高频问题。
- 多轮追问保留上下文，减少重复说明。
- 转人工时带上问题摘要、已查资料和缺失信息，减少客服二次询问。
- 无依据或复杂纠纷及时转人工，避免反复生成错误答案。

#### 为什么可能提升

一部分重复问题不再需要人工逐次查资料、组织答案；需要人工处理的问题也能更快进入判断和处理环节。

#### 怎么验证

- 记录咨询意图、是否转人工、人工处理时长及最终解决状态。
- 按咨询量和问题类型归一化比较，避免直接比较总工单数。
- 观察同一问题的重复提问、后续转人工、工单重开和抽样回访。

**用户没有点击转人工，不代表问题已经解决。有效降低人工工作量依赖正确解决问题，不能只靠隐藏人工入口。**

### Q20. “满意度达到94%”怎么测，为什么会提升？

#### 指标定义

可在咨询结束后采用五分制评价，提前固定“4分和5分为满意”的口径。

```text
CSAT满意度 = 满意评价数 ÷ 有效评价数
```

#### 实现方法

- 降低等待时间，让用户及时获得有用答复。
- 对不同问法给出一致、符合当前政策的回答。
- 展示证据和适用条件，减少用户反复确认。
- 无法解决时清楚解释原因，并提供顺畅的人工服务路径。

#### 为什么可能提升

响应更快、规则更一致、答案可核对、复杂问题能顺畅交给人工，可能改善体验。但过度拒答、回答错误和难以联系人工也可能降低满意度，不能只优化速度。

#### 怎么验证

同时报告有效评价数量、邀请评价数量、评价响应率，以及失败和转人工场景是否被纳入。区分首次咨询与重复咨询，关注选择性评价造成的偏差。

**94%的满意度与94%的答案正确率是不同指标。**

### Q21. “覆盖90%以上常见问询场景”怎么定义？

#### 先建立场景分类

从真实咨询记录建立意图分类，例如交通、设施、宠物、退订、入住、天气、投诉，再统计各类问题的实际频次。

对每类问题判断：

- 是否有足够资料。
- 能否正确回答并提供必要依据。
- 是否需要实时业务工具。
- 是否属于必须交给人工处理的情形。

不能只看文档里有没有对应标题。

#### 指标口径

```text
场景覆盖率
= 达到验收标准的场景类别数 ÷ 纳入范围的场景类别数

按频次加权的有效解决覆盖率
= Σ（各类问题实际占比 × 该类问题有效解决率）
```

#### 为什么需要加权

“停车怎么走”一天出现很多次，与很少出现的特殊活动申请，不应在工作量收益里拥有同样权重。

#### 实现方法

先补足高频问题的可靠资料，再解决口语表达、条件缺失、多轮追问和异常情况，最后在独立问题集上验收。

**问询覆盖率与六城营地命名查询Hit@5是两种不同指标。知识库有资料也不自动等于用户问题被有效解决。**

### Q22. 怎么证明提升确实来自系统？

**参考回答：**

有真实业务条件时，优先做同期对照，按用户或会话分组，一组走原流程，一组使用智能体，比较响应、人工工时、解决率和满意度。

如果只能做上线前后比较，就尽量选择相近时间窗口，控制工作日与节假日、咨询量、问题难度和客服人数等差异。

技术上再做消融实验：同一批问题分别跑BM25、向量、混合检索和重排序方案，保持模型与提示词等条件一致，判断提升来自哪个环节。

这样可以避免把促销结束、人员增加或问题变简单带来的变化，全部归因于RAG。

**实验注意事项：**

- 开发集用于调参数，独立验收集在调参前冻结。
- 不因结果不理想而删除失败、超时或难题。
- 模板题、口语题、多轮题和边界题分别报告。
- 同时观察质量、延迟和成本，避免单指标优化。

## 7. 评测与项目边界问答

### Q23. 项目怎么评测？

**参考回答：**

我把评测分成四层，不用一个准确率概括整个系统。

| 层次 | 主要问题 | 指标或检查 |
| --- | --- | --- |
| 检索 | 正确资料有没有被找到 | Hit@5、排序质量、多证据是否齐全 |
| 回答 | 回答是否正确且受到证据支持 | 正确率、引用支持、无依据时的处理 |
| 业务操作 | 有没有完成正确操作 | 工单成功、权限隔离、确认、幂等 |
| 运营效果 | 是否真正改善服务 | 完整响应时间、人工工时、满意度 |

**Hit@5的解释：**对有预先标注标准证据的问题，前5条检索结果中至少有一条标准证据即算该题命中。它不直接衡量回答正确性；需要多份证据的问题，还应检查证据是否齐全。

#### 当前可引用的项目记录

| 记录 | 样本与结果 | 限制 |
| --- | --- | --- |
| 2026-11-05知识检索 | 86条有标准证据的问题，限定营地Hit@5为82/86；其中口语复杂题22/26 | 虚构资料、小规模基线；不是独立真实运营效果 |
| 2026-11-05真实对话 | 34条计分用例，完整回答P95为4.40秒 | 单轮评测、串行负载，不能当成当前所有场景的SLA |
| 2026-11-09六城命名 | 30个独立命名样本，确认命中11/30 | 未达至少26/30门槛；另4题身份或地址待核实 |
| 2026-11-09六城泛查 | 展示30条，8条已独立核实、22条待核实 | 26.7%是已核实比例下界，不是确定的实际准确率 |
| 2026-11-09地图搜索耗时 | 36次搜索P50为151ms、P95为280ms | 不包含模型、详情或人工核验 |

证据：[知识与对话评测](EVALUATION.md) · [六城评测报告](CAMPSITE-PILOT-RESULTS.md)。

**不能混淆：**82/86的知识检索与11/30的地图命名查询，不是同一任务、数据集或指标对象。

### Q24. 六城命中率不高，是不是RAG没有效果？

**参考回答：**

不能直接这样判断。六城评测主要检查地图地点发现和身份匹配，而知识RAG评测检查文档检索与回答，失败原因不同。

六城结果暴露了充电站混入、其他分店被返回、部分名称查不到，以及独立身份资料不足等问题。它说明接通MCP只是完成接口集成，还需要业务筛选和独立验收。

下一步先区分上游未召回、后端误过滤、候选不相关和身份未核实，再针对具体原因修复。

**要理解：**不是所有问题都能靠换一个更强的大模型解决。错误可能发生在数据、检索、过滤、排序或身份匹配环节。

### Q25. 项目最大的价值和当前最大的不足分别是什么？

**参考回答：**

价值是把地点查询、规则问答和人工服务衔接起来，同时让回答有来源、资料有版本、业务操作有确认和权限约束。

当前不足是：真实营地规则资料仍不充分，向量混合检索和重排序尚未完成完整联调，地图命名召回未达标，也缺少真实运营对照数据。

因此下一步是先补数据与评测，再按瓶颈引入检索优化，最后验证业务收益。

### 8.2 建议能演示的五条流程

1. 用户查营地，查看某个候选，继续追问规则。
2. 有审核资料时，回答并打开对应引用。
3. 没有可靠资料时，说明缺口，不套用其他营地规则。
4. 生成投诉草稿，用户确认后创建工单，重复确认不重复创建。
5. 运营上传和审核资料，发布新版本后检索只使用当前可见版本。

每条演示都应说明使用的是本地演示数据、审核规则资料还是真实地图地点。
